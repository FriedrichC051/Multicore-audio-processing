## 一、8 篇硕士论文的核心内容与课程相关研究点

### 1.《并行计算框架在 RTEMS 操作系统上的实现》（张思凡）

- **核心内容**：在开源嵌入式实时操作系统 RTEMS 上，设计并实现了一个轻量级异构并行计算框架 **MPCL**（融合 OpenCL 和 MPI 思想），解决了传统单核/实时操作系统无法高效驱动多核及异构设备并发计算的痛点，构建了跨节点/跨核的任务分发、通信机制与算子注册执行体系。
- **课程相关研究点（最多 2 个）**：
  1. **实时操作系统（RTOS）下轻量级并行框架 API 与任务分发机制**
     - **结合点**：指导学生在 RTEMS/FreeRTOS 环境下，如何解耦控制节点与计算节点，设计极简的任务注册与下发接口。
     - **对应章节**：第三章《并行计算框架 MPCL 的设计》（3.1–3.3 节）、第四章《基于 RTEMS 操作系统的并行计算框架的实现》（4.1–4.2 节）。
  2. **跨核/跨节点 Socket 异步通信协议与缓存管理系统**
     - **结合点**：探讨连续音频帧流式推流时，如何通过对象序列化、自定义协议报文与内存缓存区管理降低交互延迟。
     - **对应章节**：第三章（3.4 通信模块设计、3.5 缓存模块设计）、第四章（4.3 通信模块实现、4.4 缓存模块实现）。

### 2.《基于 OpenCL 的并行计算在嵌入式推理框架中的应用研究》（韩金铭）

- **核心内容**：针对部分嵌入式/国产 GPU 缺少原生 OpenCL 驱动的问题，在 Vulkan 驱动之上构建了 **Vulkan-based OpenCL 运行时层**；并在此基础上开发与优化了 OpenCL 卷积算子（含 Winograd 与 GEMM 分块），作为 NCNN 的 GPU 加速后端。
- **课程相关研究点（最多 2 个）**：
  1. **无原生驱动平台上的 Vulkan-to-OpenCL 运行时（Runtime）映射与对象抽象**
     - **结合点**：引导学生理解 OpenCL 的核心抽象对象（Context、Queue、Buffer、Kernel）如何在低层图形 API（Vulkan/clspv）上进行桥接重构，解决驱动缺失难题。
     - **对应章节**：第三章《基于 Vulkan 的 OpenCL 运行时层设计与实现》（3.1–3.4 节）。
  2. **卷积算子的连续访存、向量化（vload）与 GEMM 分块专用优化**
     - **结合点**：指导学生将音频 FIR 空间卷积转化为连续访存与向量化加载（如 vload4/vload8），消除非连续跨步访存带来的 GPU 停顿。
     - **对应章节**：第四章《基于 OpenCL 框架的卷积算子实现与优化》（4.2–4.4 节）。

### 3.《基于 FT-M7002 的 OpenCL 移植与实现》（张望）

- **核心内容**：围绕国产 FT-M7002 异构多核处理器（RISC CPU 主控 + FT-Matrix DSP 运算核），建立了 OpenCL 四大抽象模型到实际 DSP 硬件单元（SPE/VPE/SPU/VPU/片上存储）的映射关系；基于 Clang/LLVM 与 PoCL（Portable Computing Language）完成了 OpenCL 框架的交叉编译移植与测试。
- **课程相关研究点（最多 2 个）**：
  1. **OpenCL 抽象模型到嵌入式 DSP/CPU 异构硬件架构的映射设计**
     - **结合点**：引导学生掌握如何将抽象的 Host/Device/CU/PE 与具体芯片上的主控 CPU、DSP 向量核及片上内存进行一一映射。
     - **对应章节**：第四章《面向 FT-M7002 的 OpenCL 代码生成方法实现》（4.1–4.2 节）。
  2. **基于 PoCL 与 LLVM/Clang 的嵌入式 OpenCL 交叉编译工具链构建**
     - **结合点**：指导学生如何在 x86 宿主机上编写 Toolchain.cmake 脚本，将开源 PoCL 运行时交叉编译并部署到目标嵌入式硬件。
     - **对应章节**：第五章《基于 FT-M7002 的 OpenCL 移植实现》（5.1–5.7 节）。

### 4.《基于 GPU 的 OpenCL 深度学习算子库的开发与实现》（陈柯颖）

- **核心内容**：基于国产 GPU（HCC1400）及 NVIDIA GPU，设计并实现了 32 个 OpenCL 深度学习算子；重点探索了指令优化、访存优化（SRAM/DDR）、NDRange 参数配置优化及 Warp 内展开/归约操作，并完成了基于 TIM-VX 框架的算子库集成。
- **课程相关研究点（最多 2 个）**：
  1. **OpenCL 硬件存储模型映射（SRAM/DDR/L1/Cache）与合并访存优化**
     - **结合点**：指导学生在 GPU 内存层级下利用片上 Local Memory/SRAM 做数据分块与缓存，减少对片外高延迟 DDR 的直接访问。
     - **对应章节**：第二章（2.3 存储模型映射关系）、第三章（3.3 基于其特性的算法优化策略——访存优化）。
  2. **NDRange 索引空间划分与 Warp 内自同步/循环展开优化**
     - **结合点**：探讨音频多声道与多采样点在 NDRange 映射时的 Global/Local Work-size 划分规则（匹配硬件波前/Warp 宽度）。
     - **对应章节**：第三章（3.3 节关于 NDRange 优化与 Warp 展开）、第四章（4.1 OpenCL 实现与优化）。

### 5.《基于 OpenCL 并行框架的异构系统计算加速研究》（顾经纬）

- **核心内容**：针对异构多设备（如 HXDSP/CPU）场景，提出了基于代码分析转换的"单 OpenCL 内核分解与多设备协同执行"模式；同时研究了从 OpenCL 应用中提取任务有向无环图（DAG），并提出 **HDGEFT 异构调度算法**实现多 Kernel 在多设备上的负载均衡。
- **课程相关研究点（最多 2 个）**：
  1. **单 OpenCL Kernel 的负载切分（Kernel Decomposition）与多设备协同**
     - **结合点**：把一个大阶数的音频卷积 Kernel 动态切分为多个子任务块，分发到 CPU 和 DSP/GPU 上并行计算，再通过数据合并 Kernel 汇总。
     - **对应章节**：第三章《基于代码分析和转换的单内核多设备计算模式》（3.3.1 节内核分解、3.3.2 节全局内存管理）。
  2. **基于 AST/API 提取 OpenCL 任务图（DAG）与异构调度算法（HDGEFT）**
     - **结合点**：分析复杂多声源/多滤波算子之间的依赖关系，构建 DAG 图并依据设备亲和性与计算开销做启发式调度。
     - **对应章节**：第四章《基于 HXDSP 异构系统的 OpenCL 内核调度算法》（4.2 节任务图获取、4.3 节 HDGEFT 算法）。

### 6.《基于异构计算的嵌入式系统开发框架研究》（胡楠）

- **核心内容**：针对 CPU-FPGA-GPU 耦合异构系统，提出了**"服务体—执行流"（Servant-Execution-Flow, SEFM）**异构编程模型；设计了扩展 OpenCL 的运行环境，支持双缓冲执行流、合成服务体与多通道存储；并提出了基于均匀流水线的启发式任务划分与映射算法。
- **课程相关研究点（最多 2 个）**：
  1. **"服务体—执行流"异构编程模型与 OpenCL 运行时扩展**
     - **结合点**：将空间音频处理算法解耦为独立服务体（Servant），通信与同步抽象为执行流（Flow），降低复杂异构系统的开发门槛。
     - **对应章节**：第三章《基于 SEFM 模型的应用设计》（3.1–3.4 节）、第五章（支持异构计算的 OpenCL 扩展体系结构）。
  2. **双缓冲执行流（Double-Buffering Flow）与多通道内存通信优化**
     - **结合点**：利用双缓冲流水线掩盖总线/PCIe 传输延迟，实现音频数据"边传输、边计算"的无缝衔接。
     - **对应章节**：第四章《面向异构计算的服务体间通信》（4.2 节双缓冲执行流、4.3 节多通道存储）。

### 7.《面向异构嵌入式加速内核的统一编程接口设计》（邓宇志）

- **核心内容**：基于 Zynq（ARM+FPGA）嵌入式平台，针对定制硬件加速器驱动繁琐的问题，设计了一种基于 OpenCL 抽象模型的"统一编程接口"（驱动层 + 包含 CP/DMA/仲裁器的硬件中间层），使 FPGA 端的多个硬件计算单元（FFT、矩阵求逆等）能通过同一套驱动和标准的命令/数据通道被下发执行。
- **课程相关研究点（最多 2 个）**：
  1. **OpenCL 驱动层与硬件中间层（Command Processor / DMA 引擎）的解耦设计**
     - **结合点**：帮助学生理解软件 Host 驱动如何通过轻量级 AXI-Lite 寄存器与 AXI-Full DMA 引擎进行跨总线的命令下发与数据搬运。
     - **对应章节**：第二章（2.1–2.3 支持统一编程接口的异构计算系统结构与总体框图）、第三章（3.1 硬件中间层实现）。
  2. **面向硬件加速内核的通用流式接口（Req/Rsp & 描述符通道）与可变分区内存管理**
     - **结合点**：规范硬件加速算子的输入输出通道接口，以及驱动层中最佳适应/最先适应的可变动态内存分配策略（PMM）。
     - **对应章节**：第三章（3.1.2 计算单元模块接口、3.2 驱动层可变分区内存管理系统）。

### 8.《国产推理框架 NCNN 在 AMP 架构上的适配与优化研究》（吴汶珀）

- **核心内容**：针对 RK3568 等嵌入式 **AMP 架构（Linux 主核 + RT-Thread 从核）**，设计并实现了 NCNN-AMP 加速层；围绕算子融合、无锁环形队列（Lock-free Ring Buffer）、缓冲区复用与生命周期管理、权重布局重排、数据 64 字节对齐和冷热数据分层存储开展了多维优化。
- **课程相关研究点（最多 2 个）**：
  1. **Linux 主核 ↔ RTOS 从核的无锁环形队列（Lock-free Ring Buffer）与缓冲区生命周期管理**
     - **结合点**：**极其契合课程方向一/方向二！**指导学生如何消除跨 OS 通信时的互斥锁开销，通过共享内存无锁队列实现高频 1024 帧音频块的低延迟跨核交互。
     - **对应章节**：第三章（3.3.2 通信管理器详细设计）、第五章（5.3.1 无锁环形队列优化、5.3.2 缓冲区复用与生命周期管理）。
  2. **共享内存访问效率优化：数据 64 字节对齐、权重重排与冷热数据分层存储**

## 三、具体参考

## 专题一：OpenCL 异构计算与硬件加速深水区（OpenCL & Heterogeneous Acceleration）

### 研究点 1：Vulkan/PoCL 轻量级 OpenCL Runtime 抽象与统一命令/描述符通道

#### 1.1 研发背景与痛点

许多嵌入式 GPU 或国产加速芯片未提供完整的 OpenCL 驱动。然而，大部分现代芯片均提供低开销图形与计算 API **Vulkan**。如果直接用 Vulkan 编写音频算法，代码冗长且管线控制过于繁琐；若能构建一层透明的 **Vulkan-to-OpenCL 运行时（Runtime）**，则可直接运行标准的 OpenCL C 算子。

#### 1.2 核心技术原理

- **运行时对象抽象映射**：将 OpenCL 的核心句柄（`cl_context`、`cl_command_queue`、`cl_mem`、`cl_kernel`）封装为对应的 Vulkan 计算对象（`VkInstance`、`VkDevice`、`VkQueue`、`VkBuffer`、`VkPipeline`）。
- **SPIR-V 编译与描述符映射**：借助开源编译器 clspv，将 OpenCL C 源码编译为 Vulkan 兼容的 SPIR-V 中间表示。clspv 会自动将 Kernel 参数（如指针、标量）映射为 Vulkan 的 `VkDescriptorSet` 描述符集绑定槽。
- **管线与缓冲池复用**：为避免逐帧创建 `VkBuffer` 和 `VkPipeline` 导致的耗时，在 Runtime 中设计预分配缓冲区复用池与管线缓存（Pipeline Cache）。

#### 1.3 动手实战任务与步骤

1. **构建 Runtime 结构**：实现 `clCreateContext` 与 `clCreateBuffer` 接口，底层调用 `vkCreateBuffer` 并通过 `vkAllocateMemory` 绑定设备内存。
2. **内核参数绑定**：拦截 `clSetKernelArg` 调用，记录参数对应的 `VkBuffer` 指针，在提交 `vkCmdDispatch` 前统一更新描述符集。
3. **音频流验证**：通过该运行时下发 512 阶 FIR 空间音频卷积 Kernel，校验输出数据与标准 OpenCL 驱动输出是否逐样本一致（MSE = 0）。

#### 1.4 必读论文与章节参考

- **韩金铭硕士论文**：《基于 OpenCL 的并行计算在嵌入式推理框架中的应用研究》，**第三章**《基于 Vulkan 的 OpenCL 运行时层设计与实现》（3.1–3.4 节，第 13~55 页）。
- **张望硕士论文**：《基于 FT-M7002 的 OpenCL 移植与实现》，**第五章**《基于 FT-M7002 的 OpenCL 移植实现》。

### 研究点 2：连续访存重排、向量化（vload4/8）、Local Memory 与双缓冲流水线

#### 2.1 研发背景与痛点

朴素的 OpenCL FIR 卷积 Kernel 在执行时，每次读取音频点与 HRIR 系数都是标量读取（如 short / float）。由于声音数据与 HRTF 系数在显存中可能存在跨步访问（Stride Access），这会导致 GPU 显存总线带宽利用率极低、Cache 频繁失效。

#### 2.2 核心优化机制

- **权重布局预重排**：在模型加载阶段，将 HRIR 权重从原始离散布局 `[OC, IC, KH, KW]` 重排为连续交错布局 `[IC, OC, KH, KW]`。固定输入通道时，不同输出通道的权重在内存中连续排列，一条向量指令即可连续读出。
- **向量化加载（vload4）与点积（dot）**：在 Kernel 内部使用 vload4 一次性读取 4 个连续采样点，并调用硬件原生的 `dot()` 向量点积指令，使访存指令数直接降至原来的 1/4。
- **Local Memory 片上缓存**：利用工作组（Work-group）共享的极速片上 SRAM（`__local` 内存），由组内 Work-items 协同将 HRIR 系数批量一次性加载至 Local Memory 中，消除对全局显存（Global Memory）的重复读取。
- **Pinned Memory 与双缓冲流水线**：主机端使用 `CL_MEM_ALLOC_HOST_PTR` 或 `clEnqueueMapBuffer` 申请页锁定内存；设计两个异步 Buffer（A/B），在 GPU 渲染 Buffer A 的同时，CPU 异步传输下一个音频块到 Buffer B，实现"传输与计算重叠"。

#### 2.3 伪代码框架与核心 Kernel

```c
// OpenCL 向量化与 Local Memory 缓存 FIR 卷积 Kernel
__kernel void fir_vectorized_local_kernel(
    __global const float4 *data_in,   // 连续向量化输入
    __global const float4 *hrir_flat, // 重排后的权重
    __global float4 *data_out,
    __local float4 *local_hrir,       // 片上 SRAM 缓存
    int fir_vec_sz) {
    int gid = get_global_id(0);
    int lid = get_local_id(0);
    int group_sz = get_local_size(0);

    // 1. 工作组协同将 HRIR 系数加载至 Local Memory
    for (int i = lid; i < fir_vec_sz; i += group_sz) {
        local_hrir[i] = hrir_flat[i];
    }
    barrier(CLK_LOCAL_MEM_FENCE);      // 组内屏障同步

    // 2. 利用 vload4 与向量点积计算
    float4 sum = (float4)(0.0f);
    for (int i = 0; i < fir_vec_sz; i++) {
        float4 in_val = data_in[gid + i];
        float4 coeff = local_hrir[i];
        sum += in_val * coeff;         // SIMD 向量乘加
    }
    data_out[gid] = sum;
}
```

### 研究点 3：单 Kernel 动态切分（Kernel Decomposition）与 DAG 任务图异构协同调度

#### 3.1 研发背景与痛点

当音频系统包含多个复杂声源或叠加空间混响时，单一 GPU 可能因计算过载而打破 **23.22ms** 的硬实时约束。如果系统中同时存在 CPU、多核 GPU 或 DSP，如何将同一个大阶数卷积 Kernel 切分到多个异构设备上联合执行，是榨干系统全局算力的关键。

#### 3.2 核心技术原理

- **Kernel 动态分解（Kernel Decomposition）**：分析 OpenCL 内核源码的全局内存访问模式，将 1024 帧的 NDRange 索引空间切分为若干工作组子集，生成对应子设备的"切分内核"与"数据汇总内核"。
- **任务有向无环图（DAG）提取**：通过拦截 OpenCL 命令队列（Command Queue）的入队 API 或分析语法树（AST），提取多声源/多滤波算子之间的依赖关系与数据传输边，构建包含计算开销表的 DAG 图。
- **HDGEFT 异构调度算法**：在经典 HEFT 列表调度算法基础上，结合异构设备算力差异与 PCIe 传输开销，计算任务节点的优先级，动态将 Kernel 子块分发到 CPU 和 GPU/DSP 上并行计算。

#### 3.3 动手实战任务与步骤

1. **DAG 构建**：为 8 个并发空间声源的 FIR 滤波与混音算子构建 DAG 图，测量各节点在 CPU 和 GPU 上的真实执行开销。
2. **负载切分**：将大声源的 1024 点卷积分割（例如 CPU 处理前 256 点，GPU 处理后 768 点），异步提交至各自的 `cl_command_queue`。
3. **评估加速比**：测量联合执行时间，验证其是否比单设备执行提升 15%~25% 以上的吞吐量。

## 专题二：全志 T113-i / T153 AMP 架构与嵌入式 OS 跨核协同（AMP & RTOS Integration）

### 研究点 4：Linux（Cortex-A）↔ RTOS（RISC-V）共享内存无锁环形队列与零拷贝通信

#### 4.1 研发背景与痛点

在全志 T113-i / T153 等 **AMP（非对称多处理）架构**芯片上，Linux 主核（ARM）负责复杂的音频解码与 UI，从核（RISC-V / Cortex-M）运行 RTOS/裸机进行高确定性的音频 DSP 计算。若采用通用 OpenAMP/RPMsg 框架，其内部的带锁队列与多次内核拷贝会引入不可忽视的延迟抖动。

#### 4.2 核心技术架构

- **物理共享内存静态分区**：在系统 RAM 中划分出独立的共享内存池，分为元数据区、输入缓冲区、输出缓冲区和通信缓冲区。
- **无锁环形队列（Lock-Free Ring Buffer）**：队列底层采用固定容量的循环数组，仅由头指针 Head（读取方更新）与尾指针 Tail（写入方更新）维护。入队与出队操作不需要互斥锁（Mutex）或临界区保护，完全依靠索引回绕与原子操作推进。
- **Mailbox 硬件中断唤醒**：写入方完成入队后，触发硬件 Mailbox 中断通知远端核心；远端从核在 ISR 中唤醒任务进行处理，避免 CPU 轮询空转。

#### 4.3 共享内存无锁队列实现伪代码与结构

```c
// 共享内存无锁环形队列控制结构
typedef struct {
    volatile uint32_t head;   // 读指针（由接收方/出队更新）
    volatile uint32_t tail;   // 写指针（由发送方/入队更新）
    uint32_t capacity;        // 槽位总数
    uint32_t slot_size;       // 每个槽位数据块大小（例如 sizeof(TaskDesc)）
    uint8_t buffer[];         // 预分配的静态共享内存槽位（柔性数组成员）
} LockFreeRingBuffer;

// 无锁入队函数（Linux 主核下发任务）
int lockfree_queue_enqueue(LockFreeRingBuffer *ring, const void *msg) {
    uint32_t current_tail = ring->tail;
    uint32_t next_tail = (current_tail + 1) % ring->capacity;
    if (next_tail == ring->head) {
        return -1;            // 队列已满
    }

    // 直接写入共享内存槽位（零拷贝写入）
    memcpy(&ring->buffer[current_tail * ring->slot_size], msg, ring->slot_size);

    // 内存屏障，确保数据写入完成后再更新指针
    __sync_synchronize();
    ring->tail = next_tail;   // 更新写指针
    return 0;
}
```

### 研究点 5：轻量级跨核任务分发引擎与 23.22ms 实时超时硬降级机制

#### 5.1 研发背景与痛点

Linux 主核无法直接跨 OS 调用 RTOS 的函数，跨 OS 异步任务调度存在系统抖动风险。一旦从核处理某帧音频卡顿或响应超时，系统将面临缓冲区欠载（Underrun）并产生裂音。因此必须设计一套包含**标准化任务报文、双向状态监控与超时降级**的跨核执行引擎。

#### 5.2 核心技术机制

- **标准化任务描述符（Task Descriptor）**：主核将音频渲染请求封装为标准化描述符（包含 `task_id`、`sample_rate`、`buffer_shm_addr`、`hrir_azimuth` 等字段）。
- **智能任务拆分与派发**：主核的 AMPEngine 读取从核的负载与空闲状态，将多通道/多声源任务分发给空闲的从核执行。
- **23.22ms 硬实时超时检测与 CPU 降级（Fallback）**：主核发起跨核计算后，启动高精度定时器监控（如 AMPMonitor）。若从核响应时间接近 **23.22ms** 临界阈值，主核触发超时中断，强行回收信号量，并**立即唤醒 Linux 本地 CPU 单核备用函数**完成该帧渲染，确保音频推流绝对不断流。

### 研究点 6：数据 64 字节向量对齐、HRTF 热数据 SRAM 驻留与冷热分层内存管理

#### 6.1 研发背景与痛点

嵌入式处理器（ARM NEON / RISC-V Vector）在执行 SIMD 向量加载指令时，若内存起始地址未按 Cache Line（通常 64 字节）对齐，会触发二次跨边界访问，降低 30% 以上的访存效率。此外，嵌入式片上 SRAM/L1 Cache 容量有限，若将海量音频流与 HRTF 静态系数混杂存放，会导致 Cache 频发置换。

#### 6.2 核心优化机制

- **64 字节内存对齐（aligned_alloc）**：共享内存池在分配音频 Buffer 和 HRIR 变量时，统一使用 `aligned_alloc(64, size)` 动态申请，或增加 `__attribute__((aligned(64)))` 内存修饰符。
- **基于冷热识别的三层存储管理**：
  - **第一层（缓存层：L1/L2 Cache / 片上 SRAM）**：访问延迟最低，放置频繁读取的**热数据**（如 512 阶 HRIR 空间音效滤波系数）。
  - **第二层（共享内存层：Shared RAM）**：放置阶段性交互的**温数据**（如 1024 帧输入/输出 PCM 缓冲区、任务描述符）。
  - **第三层（主存层：DDR）**：放置大容量、低频访问的**冷数据**（如全套 HRTF 原始数据库文件、未解码的完整音频文件）。

void init_layered_shared_memory(void) {
